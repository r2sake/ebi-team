## 1. 結論（3行）

1. **PTY 方式で GO。** 起動ゲートを 2 個潰せば Codex TUI は PTY 上でインライン描画し、「本文 write → 500ms → `\r`」の注入が **10/10 成功**、応答も 10/10 返る。`codex app-server`（stdio JSON-RPC）への設計変更は**不要**。
2. **MCP 経由の `reply_to_master` は成立。** `-c` インラインの TOML 注入だけで ebi-control が読み込まれ、稼働中 master へ `{"delivered":["master"],"via":"notify","confirmed":true}` で着弾した（`~/.codex/config.toml` は最後まで**未作成**＝共有設定を汚していない）。
3. **idle 判定は無改造で通る。** 待機中の PTY 出力は **60 秒で 0 バイト / 0 チャンク**。現行 `IdleDetector`（既定 900ms）がそのまま使える。

## 3. 実証済みの起動形（PR-D の第一候補）

```
codex --no-alt-screen \
  -s read-only -a never \
  -c disable_paste_burst=true \
  -c check_for_update_on_startup=false \
  -c 'projects={"<repo>"={trust_level="trusted"},"<worktree>"={trust_level="trusted"}}' \
  -c 'mcp_servers.ebi-control.command="node"' \
  -c 'mcp_servers.ebi-control.args=["<repo>/dist/server/mcp/control-server.js"]' \
  -c 'mcp_servers.ebi-control.cwd="<repo>"' \
  -c 'mcp_servers.ebi-control.default_tools_approval_mode="approve"' \
  -c 'mcp_servers.ebi-control.env={EBI_CONTROL_URL="http://127.0.0.1:8787",EBI_MCP_ROLE="engineer",EBI_ID="<agentId>",EBI_NOTIFY_SUBSCRIBE="off"}' \
  "<役割プロンプト>\n\n<初回タスク>"
```

PTY 側は `pty.spawn("codex", args, { name: "xterm-color", cols: 80, rows: 30 })`（＝現行 `agent.ts` と同条件）で問題なし。

### 3.1 設計書になかった必須フラグ 3 つ（今回の最大の収穫）

| フラグ | 無いとどうなるか |
|---|---|
| `-c check_for_update_on_startup=false` | 起動直後に **「✨ Update available! 1. Update now / 2. Skip / 3. Skip until next version」ダイアログ**で停止。無人 spawn が死ぬ（0.153.2 が出ている今、必ず出る） |
| `-c 'projects={"<path>"={trust_level="trusted"}}'` | **フォルダ信頼ゲート**「Do you trust the contents of this directory? 1. Yes, continue / 2. No, quit」で停止。worktree は git サブディレクトリ扱いなので **repo root と worktree の両方**を trusted に入れるのが安全 |
| `-c 'mcp_servers.<name>.default_tools_approval_mode="approve"'` | MCP ツール呼び出しのたびに **「Allow the ebi-control MCP server to run tool "reply_to_master"? 1. Allow / 2. Allow for this session / 3. Always allow / 4. Cancel」**で停止。**`-a never` では抑止されない（承認系統が別）**。`reply_to_master` が永久に飛ばない＝最悪の静かな故障になる |

- `default_tools_approval_mode` の値域は **`auto` / `prompt` / `writes` / `approve`**（`never` を渡すと `Error loading config.toml: unknown variant` で即 exit 1）。**`auto` ではダイアログが出た。自動承認は `approve`。**
- ドット記法の `-c projects."<path>".trust_level="trusted"` は**効かない**（黙って無視されゲートが出る）。**インラインテーブル形式** `-c 'projects={"<path>"={trust_level="trusted"}}'` を使うこと。
- `--strict-config` は未知キー/不正値の早期検知に有効（上記の `never` エラーはこれ無しでも出た）。PR-D の起動前チェックに入れる価値あり。

### 3.2 `~/.codex` の扱い

- **`~/.codex/config.toml` は PoC 前後を通じて未作成**。trust / update / approval をすべてインラインで潰したので、ボスの共有設定は無傷。
- ただし `~/.codex/{history.jsonl,logs_2.sqlite,memories_1.sqlite,models_cache.json}` などの**セッション状態 DB は codex を起動するだけで書かれる**（回避不可）。per-エビで分離したい場合のみ `CODEX_HOME` フォールバックを検討する（PoC では不要と判明）。

|---|---|---|---|
| 1〜8 | ○ | ○ | 1,808〜2,115 |
| 9 | ○ | ○ | 2,415 |

**10/10（送信・応答とも 100%）。** 判定は「①注入直後に working インジケータ（`esc to interrupt`）が出る＝送信成立」「②プロンプトに含まれない語（`PONG-X` の X を i に置換させた `PONG-<i>`）が出る＝応答成立」の 2 段。composer へのエコーを応答と誤認しないよう、判定語はプロンプト側に出さない設計にしてある。

### 4.2 idle 観測（応答完了後・無入力 60 秒）

| 区間 | 出力バイト |
|---|---|
| 5s 刻み × 12 区間 | すべて **0** |
| 合計 | **0 バイト / 0 チャンク** |
| 観測終了時の quiet | **62,026ms** |

→ 現行 `IdleDetector`（`EBI_IDLE_MS` 既定 900ms）で **idle に落ちる**。backend 別 `idleThresholdMs` の引き上げも、「同一フレーム抑止フィルタ」も**不要**。

### 4.3 タイミング

| フェーズ | 所要 |
|---|---|
| spawn → 起動出力が止まる（初回プロンプト応答込み） | 7.3 秒（出力 28KB / 166 チャンク） |

## 5. PR-D 実装への推奨

1. **PTY 方式で実装して良い（`app-server` は保険のまま据え置き）。** R1（PTY 注入）・R2（永久 busy）はいずれも実測で解消。
2. **`CodexBackend` の起動ゲート対策は「ダイアログ自動応答」ではなく「設定で出させない」**（§3.1 の 3 フラグ）。ebi-team 側の起動ゲート自動応答（`autoAnswerStartupGates`）を codex に広げる必要はない＝承認の自動クリックという危険な機構を増やさずに済む。
3. **`projects` の trust は「repo root と cwd の両方」を入れる**。worktree 運用では cwd が git サブディレクトリになり、信頼は repo root に適用される旨のメッセージが出るため。
4. **`default_tools_approval_mode="approve"` は ebi-control（自前 MCP）にだけ付ける**。他の MCP サーバへ横展開しない（`mcp_servers.<name>` 単位で閉じるのが安全）。
5. **MCP 起動と初回プロンプトの競合に注意。** 初回プロンプトを位置引数で渡すと boot 中に `⚠ MCP startup interrupted. The following servers were not initialized: codex_apps, ebi-control` が出た。その後のツール呼び出しは成功しているが（遅延起動される）、PR-D では「初回タスクは MCP 起動完了後に注入」または `mcp_servers.<name>.startup_timeout_sec` の明示を検討する。
6. **`codex_apps` という組み込み MCP が常に 1 本起動する**（`Starting MCP servers (0/2): codex_apps, ebi-control`）。プロセス勘定・kill 時の後始末はこれを前提にする。
7. **permissionMode 写像は Q-7 の推奨（読み取り寄り）でそのまま運用可能。** `-s read-only -a never` は「ファイル読解タスクは普通に通る／承認待ちで固まらない」ことを実測済み。`-a on-request` は無人運用では固まるので**使わない**。
8. **バージョン固定の記録を。** 0.146.0 で検証、0.153.2 が既にリリース済み。`--version` を起動時に記録し、想定外なら警告（R6 対策）。`default_tools_approval_mode` の値域はバージョン差で動きうる箇所。

## 6. 未解決 / 注意事項

- **一度だけ、起動 3.2 秒後に codex が exit 0 で自然終了した**（フォルダ信頼ゲート表示直後、無入力の状態）。同条件の再現試行（15 秒 × 4 パターン）では再現せず、ゲートを潰した後は 1 度も発生していない。PR-D では「ready 到達前の予期せぬ exit」を検知してリトライ or 明示エラーにするのが無難。
- 今回の PoC は `reply_to_master` のみ検証。`list_ebi` / `read_scrollback` 等 engineer 向け他ツールは未検証（同じ MCP サーバなので追加リスクは低い）。
- 稼働 master には PoC 疎通メッセージが 2 通着弾している（`[poc-codex]` タグ付き、`nonce=234940` / `nonce=473334`）。
